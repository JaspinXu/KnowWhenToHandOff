# ADR-001: Trainer and GPU software stack

- Status: **Accepted for implementation** (29 Sep 2026); the T0.4 spike on the
  cluster (step time, go/no-go) is still to be recorded below.
- Related tasks: T0.3, T0.4, T2.2, T3.1–T3.4
- Supersedes: ADR-007 (the evaluation client is tau2's own LiteLLM path)

## Context

The study needs multi-turn RL where only policy tokens receive gradient (GRPO),
on one 141 GB GPU, and an evaluation path that serves the same checkpoints
with an OpenAI-compatible API for the τ²-bench runner. The cluster's NVIDIA
driver version is unknown until the first job runs.

## Decision

| Component | Pin | Role |
| --- | --- | --- |
| verl | 0.8.0 (`verl[vllm]`) | GRPO trainer; `AgentLoopBase` for token-in/token-out episodes; FSDP |
| vLLM | 0.12.0 | Rollouts inside verl; OpenAI-compatible servers for evaluation and the simulators (hermes tool parser) |
| PyTorch | 2.9.0, CUDA 12.8 wheels | Needs an NVIDIA driver >= 525 (checked by the setup job) |
| Transformers | 4.57.6 (< 5) | Models, tokenizers, SFT `Trainer` |
| LiteLLM | 1.82.6 (tau2's bound `< 1.82.7`) | tau2's client for agent and user-simulator calls |
| Python | 3.12 | |

The complete lock is `requirements/cluster-gpu.txt`, generated by
`scripts/lock_cluster_env.sh` from `requirements/cluster-gpu.in` for Linux x86_64.
Resolution uses a PyPI snapshot (`--exclude-newer 2026-06-02`, the day after
verl 0.8.0 was published) plus upper bounds on majors released after vLLM 0.12
(`pandas<3`, `openai<3`, `protobuf<7`, `starlette<1`, `datasets>=4,<5`). Without
them the resolver chose `datasets` 2.14 together with `pyarrow` 25, which cannot
even be imported; re-running the script reproduces the same lock.

Design within verl:

- `handoff.rollout.verl_loop.Tau2AgentLoop` (registered as `tau2_agent`) runs one
  τ²-bench conversation per dataset row: tau2's orchestrator in a worker thread,
  the policy on verl's server manager, token IDs kept exactly as sampled
  (`response_mask` 1 for policy tokens, 0 for user/tool tokens).
- The episode reward is computed inside the loop and returned as
  `reward_score`, with every term in `reward_extra_info`; the configured
  reward function (`rollout/verl_reward.py`) raises if verl ever calls it.
- `handoff.train.verl_main` is verl's `main_ppo` with a task runner that
  exports every saved actor checkpoint to a bf16 Hugging Face directory (verl's model merger; LoRA
  adapters merged) as soon as it is written. The presets save only resumable
  state (`model`, `optimizer`, `extra`: ~50 GB for a 4B actor, whose FSDP
  weights are float32) and keep one such checkpoint
  (`max_actor_ckpt_to_keep: 1`), so a 60-step run needs ~100 GB of scratch.
- Turn budget: every policy turn may use 2,048 tokens, and an episode ends
  cleanly (`context_window_exceeded`, no format error) when the conversation
  plus one turn no longer fits 32,768 tokens, exactly as the evaluation server
  rejects such a request. verl's response length (24,576 after an 8,192-token
  prompt budget) is a second limit, so a training episode can end up to a few
  thousand tokens earlier than in evaluation; both drivers end it the same way.
- End of a turn: the tokenizer's EOS plus every `eos_token_id` of the model's
  `generation_config.json`, the set vLLM stops on in verl and at evaluation.
- The user simulator is a separate Slurm job with a time limit. The agent loop
  re-reads its endpoint file when it changes and, after a failed episode, waits
  up to `user_sim.outage_timeout_s` for a restarted simulator before retrying;
  if none comes back, the training job stops and is resumed (`RESUME=<run id>`)
  from its last checkpoint.
- SFT (B2) uses Hugging Face `Trainer` on assistant-only token records rather
  than verl's SFT trainer, so the same records and masks serve the tokenizer
  checks; LoRA adapters are merged before saving.

## Alternatives

| Option | Why not |
| --- | --- |
| verl 0.9.x | CUDA 13 wheels need driver >= 580, unknown on the cluster |
| ART (LoRA GRPO) | LoRA-only; a possible fallback |
| TRL `GRPOTrainer` | Multi-turn environment rollouts with token masks were immature for this use |
| slime | Megatron-based; heavier setup than a one-person course project can afford |

## Verification

Done on CPU with a replica of the lock (all vLLM/verl code paths that do not
need a GPU; `tests/test_gpu_stack.py`, run by the setup job):

- verl's Hydra config composes with the GRPO preset (full and LoRA);
- vLLM's own CLI parser accepts every model's server command;
- the training Hermes parser agrees with vLLM's `Hermes2ProToolParser`;
- `Tau2AgentLoop` runs a complete toy episode through verl's `AgentLoopBase`,
  turns an episode without a policy turn into a no-gradient placeholder, and
  waits out a simulator restart;
- the checkpoint export (including a LoRA merge on a tiny model) and its hook
  into verl's trainer.

Pending (T0.4): three GRPO steps from B2 on the H100 96 GB (changed from the H200 on 3 Oct: cluster QoS) (`EXPERIMENT=SPIKE`,
runbook §7), recording step time, rollout time and peak memory here, then the
go/no-go. Fallbacks if it fails: `rl.use_lora=true`, fewer steps, or offline
rejection-sampling fine-tuning with the existing teacher → SFT path.

## Consequences

- Upgrading any pinned component needs a new lock and a new ADR.
- The cluster environment is built by `slurm/submit.sh setup`; the laptop
  environment (`uv sync`) stays CPU-only and never installs this stack.
