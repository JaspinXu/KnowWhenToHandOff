# Hand-off task set (T1.3)

Upstream τ²-bench tasks almost never require a transfer (airline task 13 is the
only upstream airline task with `transfer_to_human_agents` in its reference
solution), so calibrating hand-offs needs its own tasks. They are generated by
`src/handoff/envs/handoff_tasks.py` (`handoff_tasks_v1`) from upstream tasks,
validated with tau2's own `Task` schema and every communication style, and
written to `data/handoff_tasks/v1/<domain>_tasks.json` with hashes in
`data/manifests/handoff_tasks_v1.json`.

## Kinds

| Kind | y | What changes in the source task | Evaluation criteria |
| --- | --- | --- | --- |
| `explicit_request` | 1 | The user asks for a human agent and declines the AI agent's help (3 templates) | database unchanged **and** a `transfer_to_human_agents` call (arguments not compared) |
| `out_of_scope` | 1 | The user asks for a service no tool or policy clause covers (5 airline, 4 retail templates) | as above |
| `hard_negative` | 0 | The source task plus a difficult but cooperative user (frustrated, hurried, skeptical) who never asks for a human | the source task's own criteria |

Out-of-scope requests are outside both policies' stated scope (airline: book,
modify or cancel reservations, refunds and compensation; retail: pending and
delivered orders, the default address, profile information):

- airline: wheelchair assistance, a special meal, a lost-item search, a formal
  complaint about staff, an escort for an unaccompanied minor;
- retail: a warranty repair visit, gift wrapping, an email address change, a
  mailed paper invoice.

A fifth retail template (refund of a later price drop) was dropped on 3 Oct 2026
before the first generation: it asked for money while the user instructions say
"no compensation", and the policy arguably makes it a denial rather than a
transfer.

The user keeps the source task's identity and known information, so the agent
can authenticate normally; it does not want any change, cancellation or
compensation, and accepts a transfer if offered.

## Lineage and splits

Every derived task has the ID `<source id>__<xr|oos|hn><i>`, records its source
task, kind, template and generator version, and **inherits the split of its
source task**; the registry asserts that no source task appears in two splits.
Hard negatives are only derived from sources with y = 0. Templates rotate
deterministically (`seed` in `configs/handoff_tasks/v1.yaml`).

Variants per source task (`configs/handoff_tasks/v1.yaml`):

| Split | Airline xr / oos / hn | Retail xr / oos / hn |
| --- | --- | --- |
| train | 1 / 2 / 2 | 1 / 1 / 1 |
| dev | 1 / 1 / 1 | 1 / 1 / 1 |
| test | 1 / 1 / 2 | 1 / 1 / 1 |

With 20 airline and 40 retail test tasks this gives 40 / 80 positive and up to
40 / 40 hard-negative test episodes per trial and style (README target: ≥ 30 of
each class per domain).

## Hand-check (definition of done)

`bash slurm/submit.sh tasks` writes `reports/review/handoff_tasks.md` (a seeded,
stratified sample of 40 tasks). For each task check: the request really needs
(or really does not need) a human under the domain policy, the user
instructions are consistent, and the evaluation criteria match the kind. Drop a
template that the policy turns out to cover, record the reason, regenerate
before M1 and commit the manifests. Label corrections for upstream tasks go
into `data/manifests/label_overrides_v1.json` (see [labels.md](labels.md)).
